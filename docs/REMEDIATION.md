# Remediation — scope decision, contract, and what remains

**Phase 8, 2026-10-21. Extended by Phase 9, 2026-10-21.** This document
resolves `CLAUDE.md` §9 questions 4 and 3, and is the authority on what
remediation does in this build.

Phase 8 resolved question 4 (is remediation in scope?) as "yes, as a reviewed
proposal workflow". Phase 9 resolved question 3 (is video reconstruction in
scope?) as **yes, from an owner-supplied replacement image** - see §9 below for
that decision and its limits.

Questions 2 (MongoDB vs DynamoDB), 7 (Nova Act) and 9 (deployment target) are
untouched and remain open.

> **The one-line summary.** An owner can propose a correction, approve it,
> supply the replacement image themselves, have the backend build a **new**
> video with it, and see what a fresh analysis **of that new video** found.
> Their original upload is never modified. Automated image generation is still
> not implemented. Nothing in this phase has run against real AWS, and FFmpeg
> was not available on the machine it was written on - so the reconstruction
> code is covered by subprocess-boundary tests and its real-binary tests are
> **skipped**, not passing.

---

## 1. The decision

> **Remediation is in release scope as a reviewed proposal workflow (Phase 8)
> plus a real correction built from an owner-supplied replacement image
> (Phase 9). Automated image generation is still not implemented, and no Nova
> Canvas adapter ships.**

What that means concretely:

| Capability | Status |
| :-- | :-- |
| Propose a remediation for a persisted finding | **Implemented** (8) |
| Explain what would change, on what basis, and what it cannot guarantee | **Implemented** (8) |
| Owner approval / rejection / withdrawal, enforced server-side | **Implemented** (8) |
| Confidence threshold actually read and enforced | **Implemented** (8) |
| Staleness detection (finding changed → proposal superseded) | **Implemented** (8) |
| **Generate** a replacement image automatically | **Not implemented** — contract only |
| **Accept** an owner-supplied replacement image, validated by sniffing | **Implemented** (9) |
| Build a new output video from the source + that image | **Implemented** (9) |
| Validate the output before anything trusts it | **Implemented** (9) |
| Analyse the output through the existing pipeline | **Implemented** (9) |
| Decide verification from the output's persisted analysis | **Implemented** (9) |
| Report other / newly introduced findings separately | **Implemented** (9) |

**No image has ever been generated by this system**, and no code path can
generate one. A video *can* now be built - from an image the owner supplies -
but **the original upload is never modified** by any path: the output is a
separate object, under a separate prefix, with its own video id.

### Why generation is not implemented

The roadmap's own instruction for this phase is: *"Verify the payload schema
against current Bedrock documentation; **do not guess**."* The schema cannot
be verified from anything available here:

1. **The pinned SDK does not describe it.** `bedrock-runtime`'s `InvokeModel`
   takes `body` as an opaque **blob** — verified directly against this
   repository's own dependency:

   ```
   botocore 1.43.114
   data/bedrock-runtime/2023-09-30/service-2.json.gz
   InvokeModelRequest.body -> shape "Body", type "blob"
   ```

   So boto3 validates nothing about a Canvas request. There is no generated
   client, no typed model, no shape to read.

2. **No existing code defines it.** The one prior attempt,
   `audit_manager.remediate_frame` (deleted in Phase 5; recoverable at
   `94205bb^:backend/audit_manager.py`), carried its own admission in a
   comment — *"Since I don't have the exact Canvas schema confirmed, I'll use
   a placeholder structure"* — had its `invoke_model` call commented out, and
   encoded image bytes with `.decode('latin1')`, which is not a valid encoding
   for a Bedrock image field under any schema. It returned its input unchanged
   while its caller recorded `remediated=True`. It is evidence of the bug, not
   of the API.

3. **No document here specifies it.** `docs/planning.md` names the model and
   nothing else. `infra/iam_policy_least_privilege.json` has kept the Canvas
   grant commented out since Phase 3.5 for precisely this reason.

A guessed adapter would be worse than none: it would look implemented, pass
its own mocked tests (the mock would encode the same guess), and fail only
against the real service — after an operator had granted it model access and
pointed it at live customer video.

### Why the review workflow was worth building first

Generation is the *last* missing piece, not the first. A frame image is only
useful if something can assemble it into a video and then check the result -
which is what Phase 9 built. Shipping generation first would have produced
assets with no consumer.

### What Phase 9 did instead of guessing a provider

The provider's job is to produce image bytes. An owner can produce those bytes
themselves, so Phase 9 added that path and built everything downstream of it
for real:

* `POST /remediations/{id}/asset` takes an image, **sniffs its bytes** through
  the same validator a provider's output would pass through, and stores it
  under a server-generated key;
* `backend/reconstruction.py` builds a new video with one FFmpeg overlay pass;
* `backend/remediation_executor.py` runs that as a claimed, leased worker job
  and registers the output as a first-class video record;
* the existing analysis pipeline analyses the output, with no special case;
* `backend/verification.py` reads the output's **persisted** results and
  decides the verdict.

So the only thing still missing is the image source, and the system is honest
about which one it has: `asset_source` on the record is `"upload"`, not a
provider name.

The review workflow, by contrast, is the human-in-the-loop gate the roadmap
asks for (Phase 8 task 4, *"a human-in-the-loop queue … planned, entirely
absent"*), is fully implementable with no AWS dependency, and is testable end
to end.

## 2. The domain model

### States

Defined in `backend/remediation_state.py`. Each is a different statement about
the world and **none may be inferred from another**:

| State | What it asserts |
| :-- | :-- |
| `proposed` | A change has been described. Nobody agreed to it; nothing generated; nothing changed. |
| `approved` | An authenticated owner agreed it should be attempted. **Still nothing generated.** Waiting for a replacement image. |
| `processing` | A provider call is in flight. **Unreachable** — no provider ships. |
| `asset_ready` | A validated replacement image exists in storage. The source video is **unchanged** — a candidate, not a correction. |
| `reconstructing` | A worker holds this record and is building an output video. **Phase 9.** This is the state that carries the claim and lease, so it is what a crashed worker leaves behind. |
| `applied` | An output video exists and is registered. Its compliance is **unknown** — nothing has analysed it. |
| `verifying` | A fresh analysis **of that output** is running. |
| `verified` | A completed analysis of the output persisted results supporting the claim. The only state `is_compliance_claim` is true for — and even then it means *the targeted finding is gone*, not *the video is compliant*. |
| `rejected` | The owner declined. Terminal. |
| `cancelled` | Withdrawn before anything consequential. Terminal. |
| `superseded` | The video was re-analysed and the finding changed, so the proposal no longer describes anything real. Not a failure. Terminal. |
| `failed` | A stage failed; `error_summary` says which, safely. Terminal. |
| `verification_failed` | A re-analysis ran and did **not** support the claim. **Emphatically not clean.** Terminal. |

```
                       ┌─► processing ─┐          (unreachable: no provider)
proposed ─► approved ─►┤               ├─► asset_ready ─► reconstructing ─► applied ─► verifying
   │           │       └───────────────┘        │               │              │          │
   ├► rejected ├► cancelled                     ├► cancelled    ├► failed      ├► failed  ├► verified
   ├► cancelled├► superseded                    ├► superseded   └► asset_ready └► failed  └► verification_failed
   └► superseded                                └► failed         (crash recovery only)
```

The `approved ─► asset_ready` edge is the supplied-asset path: it skips
`processing` because there is no provider call in flight. The image is still
validated and stored before the transition, so `asset_ready` keeps its
meaning.

Properties the transition table enforces, each with a test:

- `verified` is reachable **only** from `verifying`. "Verified" therefore means
  a re-analysis ran — not that somebody decided it was fine.
- `applied` is reachable only from `reconstructing`, and `reconstructing` only
  from `asset_ready`. So an output video cannot be recorded without a run that
  built it, and a run cannot start without a validated image.
- No state transitions to itself. Repeated decisions are handled as idempotent
  no-ops by the routes, so a retry cannot overwrite `approved_at`.
- Terminal states have no exit. A new attempt is a **new proposal**, so the
  record of what was agreed stays intact.
- `reconstructing` and `applied` cannot be superseded: a worker holds the
  first, and the second has a real object behind it. `asset_ready` *can* be
  (Phase 9 changed this) — `mark_superseded` leaves `asset_key` on the record,
  so the image stays named and auditable, and without this edge a record whose
  finding changed would keep reporting "ready" while every execution attempt
  was refused.

### What this build can reach

`UNREACHABLE_IN_THIS_BUILD = {processing}` — and that is the right one to be
left, because it is the provider state.

Everything else is reachable, through the supplied-asset path. The two sets are
asserted to partition the enum, so adding a provider means deliberately moving
a name out of the unreachable set rather than leaving a stale declaration.

Phase 8 had almost the whole chain unreachable and said so; that was accurate
then. Phase 9 lifting it is the point of the phase. What has **not** changed is
how hard `verified` is to reach: it still requires a completed analysis of the
output whose persisted results support the claim, and `verification.py` is the
only module that may take that transition.

### Identity and staleness

A finding is addressed positionally: **`(video_id, frame_number,
detection_index)`**. That address is not stable — `analyzer._record_frame_result`
overwrites a frame's row, and a second Bedrock call can return a different
number of violations in a different order.

So every record also stores a **fingerprint**: a SHA-256 over the finding's
category, description, risk level, confidence and bounding box (formatted, so a
`Decimal` from DynamoDB and the `float` it was written from hash identically).
Before any consequential action the finding is re-read and re-fingerprinted; a
mismatch moves the record to `superseded` and the request answers 409.

The fingerprint deliberately excludes `detection_index` (the address, not the
content) and `timestamp_seconds` (derived from the frame number).

### Storage

MongoDB collection **`remediations`**, beside `videos` and `users`.

- **Not DynamoDB:** the lifecycle needs a conditional write keyed on the
  record's current state, which is exactly the
  `update_one(filter_including_state, {"$set": …})` + `modified_count` pattern
  `video_repo` already uses. One concurrency idiom, not two. §9 q2 stays open
  and this moves with whatever it decides.
- **Not a field on the `videos` document:** a video has many findings with
  independent lifecycles; embedding an unbounded, individually-transitioning
  array in the document the worker conditionally updates on every heartbeat
  would make two unrelated writers contend on one document.

**Migration:** purely additive. The collection is created on first insert,
`ensure_indexes` is idempotent, and no existing document is read or written. A
deployment that never calls a remediation route never creates the collection;
rolling back to a build without this module leaves it unread. `db_init`
creates the indexes (`remediation_id` unique, `owner`, `video_id`, `state`)
alongside the existing ones, non-destructively.

## 3. The API

All routes require a bearer token. Every one resolves ownership from the
video's ownership record or the remediation's stored `owner`; a request body
never carries an owner, a role, or an approver.

| Method | Path | Purpose |
| :-- | :-- | :-- |
| `GET` | `/remediations/capabilities` | What this deployment can do |
| `POST` | `/remediations` | Propose for one finding |
| `GET` | `/remediations?video_id=…` | List the caller's records for a video |
| `GET` | `/remediations/{id}` | One record |
| `POST` | `/remediations/{id}/approve` | Record the owner's approval |
| `POST` | `/remediations/{id}/reject` | Record the owner declining |
| `POST` | `/remediations/{id}/cancel` | Withdraw, including after approval |
| `POST` | `/remediations/{id}/execute` | Build the output video from the attached image |
| `POST` | `/remediations/{id}/asset` | Attach an owner-supplied replacement image (multipart) |
| `GET` | `/remediations/{id}/status` | State, the output's analysis progress, and any verdict |
| `GET` | `/remediations/{id}/output` | A short-lived scoped playback URL for the output |

### Status codes and what they mean

| Code | When |
| :-- | :-- |
| 201 | A proposal was created |
| 200 | A decision applied, or a repeat of one already applied (idempotent), or a proposal already existed for this finding |
| 400 | Malformed video id |
| 401 | No token, an expired token, or a media token (scope separation) |
| 404 | No such record/finding, **or it is not yours**, or remediation is disabled |
| 409 | Wrong state, a stale finding, a below-threshold gate, the per-video cap |
| 422 | Malformed payload, or a stored finding that cannot support a review |
| 502 | The analysis store could not be read (never confused with a missing finding) |
| 413 | The uploaded image exceeds `MAX_REMEDIATION_ASSET_BYTES` |
| 503 | No image provider is available, or reconstruction is disabled |

### Authorization, stated once

- A record that does not exist and one belonging to someone else both answer
  **404**, so these endpoints cannot enumerate ids.
- `approved_by` is written from `user["sub"]` and nothing else. A body field
  named `approved_by`, `owner` or `state` is ignored — there is a test.
- The repository layer filters **every** read and **every** conditional write
  by `owner`, so a mistake in a route cannot become a cross-tenant read.
- Concurrency is the conditional write: the filter includes the current state,
  so of two racing decisions the loser matches zero documents and gets 409.
- Proposals require the video's analysis to be `completed`. A finding is only
  a settled fact once the job reached the state meaning analysis finished and
  its results were persisted.

### Added to an existing endpoint

`GET /violations/{video_id}` now includes **`detection_index`** on each
detection. Additive and backward-compatible: no field was removed or renamed,
and a test asserts the existing keys are still present. It is needed because
`/violations` flattens detections across frames, so the browser cannot derive
a finding's index within its frame; deriving it from array position would work
only by undocumented convention and would break under different pagination.

## 4. The provider contract

`backend/image_provider.py`. One method, no storage access, no identity.

```python
class ImageProvider(Protocol):
    name: str
    def is_available(self) -> bool: ...          # no network I/O
    def unavailable_reason(self) -> str | None: ...
    def generate(self, request: GenerationRequest) -> GenerationResult: ...
```

`GenerationRequest` carries the image bytes, a **validated** region
(`[ymin, xmin, ymax, xmax]`, 0–1000, already checked for length, type, range
and ordering) and an instruction. It deliberately carries **no** S3 key, media
token, username or raw model text, so a provider cannot reach storage or
identity on its own. It is frozen, so a provider cannot mutate the region.

### Error contract

| Exception | `retryable` | Meaning |
| :-- | :-- | :-- |
| `ProviderUnavailable` | `False` | Not configured. No retry configures a provider. |
| `InvalidProviderOutput` | `False` | Answered, but not with a usable image. |
| `ProviderError` | explicit | Anything else; set **at the raise site**, never inferred from a message — the `source_store` rule. |

### Output validation

`validate_image_bytes` treats provider output as untrusted and returns the
content type **derived from the bytes**, ignoring whatever the provider
declared. It rejects: non-bytes, empty, under 64 bytes, over 16 MiB, and
anything whose magic number is not JPEG or PNG — which covers a JSON error
body, an HTML error page and a PDF, all of which arrive as bytes with a 200.

**A 2xx response is not evidence of an image.** Tests cover every case above
with deterministic payloads.

### What ships

`NullImageProvider` only. It reports `is_available() == False` and `generate`
**always raises** — it never returns input bytes, a placeholder, or a
fabricated result. That is the entire difference between this phase and the
deleted `remediate_frame`, and there is a test named for it.

Configuring `REMEDIATION_IMAGE_PROVIDER=nova-canvas` returns a
`NullImageProvider` that reports the configured name with a specific reason
naming the unverified wire format, rather than an opaque "unknown provider".
An unrecognised value is a `ConfigurationError` at startup.

## 5. Configuration

| Variable | Default | Purpose |
| :-- | :-- | :-- |
| `REMEDIATION_ENABLED` | `true` | The proposal/review workflow. `false` makes every route 404. |
| `REMEDIATION_IMAGE_PROVIDER` | `none` | `none` or `nova-canvas`; neither generates. Anything else fails at startup. |
| `REMEDIATION_MIN_CONFIDENCE` | `0.8` | Threshold `execute` enforces. The figure `docs/planning.md` has specified since Phase 1 — this is the first code to read it. |
| `MAX_REMEDIATIONS_PER_VIDEO` | `200` | Per-video cap. |
| `RECONSTRUCTION_ENABLED` | `true` | Whether an approved remediation may be built into a video. **Requires the FFmpeg executable.** Set false without it, so the API reports the capability as absent rather than accepting work every attempt would fail. |
| `RECONSTRUCTION_TIMEOUT_SECONDS` | `300` | Wall-clock bound on one FFmpeg overlay pass. |
| `REMEDIATION_WINDOW_SECONDS` | `1.0` | Half-width of the interval the image is drawn over, centred on the finding's timestamp. Widening it alters more of the video than the finding supports. |
| `MAX_REMEDIATION_ASSET_BYTES` | `8388608` (8 MiB) | Ceiling on an uploaded image, enforced on the bytes received. |
| `REMEDIATION_LEASE_SECONDS` | `600` | How long a worker's claim on a reconstruction survives without a heartbeat. |
| `VERIFICATION_POLICY` | `target_only` | `target_only` or `clean_output`; see §6d. An unrecognised value fails at startup. |

### Storage prefixes added by Phase 9

| Prefix | Holds | Lifecycle |
| :-- | :-- | :-- |
| `remediation-assets/{remediation_id}/asset.{ext}` | The replacement image an owner supplied | Expires with `SourceRetentionDays` — it is the audit record of what was supplied |
| `remediated/{output_video_id}/output.mp4` | A reconstructed output video | Expires with `SourceRetentionDays`, never sooner; nothing in the application deletes a retained output |

Both are in `aws_resources.MANAGED_PREFIXES`, both are in the IAM object
statement, and both have a CloudFormation lifecycle rule — a test asserts
every managed prefix has one. Nothing writes to `sources/`.

The confidence gate records one of `pass` / `below_threshold` /
`not_reported` on every proposal. A finding with **no** reported confidence
does not pass: absent is not the same as high, and `detections.py` keeps it
absent rather than defaulting it. Review is never gated — a human should be
able to look at a low-confidence finding; only generation is refused.

**No new BEDROCK permission is required**, because no code path calls a
provider. `infra/iam_policy_least_privilege.json` still withholds
`amazon.nova-canvas-v1:0`.

Phase 9 **does** add S3 permissions, narrowly: `GetObject`/`PutObject` on the
two new prefixes, and `DeleteObject` on them for compensating cleanup only
(an object written before its database record fails to be written is an orphan
nobody can reach). No bucket-wide grant was added, and a test asserts the
policy still grants no bucket-wide write and no Canvas access.

Nothing in `infra/` was deployed, and no live AWS resource was touched.

## 6. Implementing a real provider — the checklist

Everything a future phase and its operator must supply. Do not start until
`CLAUDE.md` §9 q3 (reconstruction) is also decided, or the assets will have no
consumer.

**Must be verified first (the blocker):**

1. The Nova Canvas `INPAINTING` request schema from authoritative Bedrock
   documentation: field names, nesting, how image and mask are encoded
   (base64, not `latin1`), size and dimension limits, and the response
   envelope. Write the citation into the adapter's docstring.

**Then, in code:**

2. Implement `ImageProvider` in a new `backend/nova_canvas_provider.py`.
   Build the client through `aws_clients` so it gets finite timeouts and a
   bounded retry budget — an unbounded call keeps a dead worker heartbeating
   and its job is never recovered.
3. Build the mask from the validated `region` and the image's **own**
   dimensions. This re-adds a **Pillow** dependency, removed in Phase 5 —
   declare and pin it in `backend/requirements.txt` (`test_dependencies.py`
   enforces that).
4. Classify every failure at its raise site. Throttling and timeouts are
   retryable; a validation rejection or an unsupported image is not.
5. Pass every byte through `validate_image_bytes` before it reaches storage.
6. Store assets under a **new** S3 prefix with server-generated keys, e.g.
   `remediated/{video_id}/{remediation_id}.png`. Add it to
   `aws_resources.MANAGED_PREFIXES`, to the IAM statement and to the bucket
   lifecycle rules together — the prefix list is a contract across all three.
   **Never overwrite the original**: `sources/` and `frames/` stay untouched.
7. Serve assets through the project's existing authorization approach (a
   short-lived scoped media token), never a public or presigned URL in a
   response body, and never log a signed URL.
8. Run generation on the **existing durable worker**, not a second queue:
   persist the claim before acknowledging, keep the lease and fencing token,
   bound the attempts. Remove `processing`/`asset_ready` from
   `UNREACHABLE_IN_THIS_BUILD` and update the test that asserts the partition.
9. Add provider tests with malformed, empty, oversized, unsupported and failed
   responses — the contract tests already exist; add the adapter's own.

**Operator steps:**

10. Request Bedrock model access for `amazon.nova-canvas-v1:0` in the region.
11. Add the `bedrock:InvokeModel` grant for that model ARN to the IAM policy
    and remove its `_NOT_GRANTED` entry.
12. Set `REMEDIATION_IMAGE_PROVIDER=nova-canvas`.
13. **Confirm cost.** Generation is billed per image, on top of the per-frame
    Nova Pro analysis cost.

## 6a. Supplying the replacement image (Phase 9)

`POST /remediations/{id}/asset`, multipart, one file.

**Nothing the client says about the file is trusted.** The declared filename
and content type are ignored for every decision:

* the size limit is enforced on the bytes **received**, in chunks, so an
  oversized body is refused part-way rather than after buffering all of it;
* the media type is determined by **sniffing the magic number**, through the
  same `image_provider.validate_image_bytes` a real provider's output would
  pass through — so a Windows executable renamed `logo.png` is refused, as are
  an empty file, a truncated one, a GIF, a PDF and an HTML error page;
* the stored extension is derived from the sniffed type;
* the object key is `remediation-assets/{remediation_id}/asset.{ext}` — built
  from the server-minted id, so no part of a filename reaches a key.

It is **not a way around review**. The record must already be `approved`, by
this caller, the finding is re-fingerprinted first, and the confidence gate is
checked before the bytes are even read. An image cannot be swapped once
attached: that would change what was reviewed, so the owner must withdraw and
propose again.

The asset is re-validated **on the way out** too, before the FFmpeg pass: the
object could have been replaced out of band, and those bytes are about to be
composited into a video a compliance claim will be made about.

## 6b. How the output video is built

`backend/reconstruction.py`. One FFmpeg pass, through `ffmpeg-python`, which
builds an **argument list** passed to `subprocess` with no shell — which
matters because the region and the window are derived from model output.

```
[0:v][1:v] overlay=x=X:y=Y:enable='between(t,START,END)'   +  -acodec copy
```

* **Audio is copied, not re-encoded**, so it is bit-identical when the source
  had any. `validate_output` refuses an output that lost expected audio.
* **Duration, frame rate and dimensions** are the source's. The output is
  checked against the source's probe and refused if the duration drifts by
  more than `DURATION_TOLERANCE_SECONDS` (1s) or the dimensions change at all.
* **Only the approved window changes**, because the overlay is enabled only
  between the finding's timestamp ±`REMEDIATION_WINDOW_SECONDS`. Everything
  outside it is the source's own frame, apart from the lossy video re-encode
  the single pass costs.

### What it is NOT

**Not seamless compositing.** The image is scaled to the approved region and
drawn over it with **hard edges**. It conceals that region; it does not
inpaint, match grain, or track motion. The audit record says
`"method": "scaled_overlay"` and the UI renders that as "Scaled overlay over
the approved region" — the word "seamless" appears nowhere, and a test asserts
that.

**Not a frame re-stitch.** `video_stitcher.py` (a legacy CLI, never on the
request path) rebuilds a video from the extracted 1 fps JPEGs. That would
discard the audio entirely, resample the footage to 1 fps, and change every
frame — so the output would differ from the original everywhere, not just where
the approved finding is. It is not used.

### When it refuses

Nothing is invented. Every number comes from the approved finding or from
probing the real file, and each of these **refuses** rather than guessing:

| Condition | Why it refuses |
| :-- | :-- |
| No bounding box on the finding | There is no region to target. Covering the whole frame would alter footage nobody approved. |
| A malformed, inverted, zero-size or out-of-range box | Same, and `detections.BoundingBox` already rejects these upstream. |
| A region under `MIN_REGION_PIXELS` (8px) on a side | Too small to cover meaningfully on this video's real dimensions. |
| No timestamp, or one past the clip's duration | The stored finding does not describe this file. |
| A window that resolves to zero time | The overlay would be enabled on no frame, so the output would equal the input — and then be analysed as if it were a correction. |
| The source cannot be probed, or has no video stream | Nothing to build from. |
| FFmpeg is not installed | Reported distinctly from a corrupt file; both are permanent. |

A refusal for any of these is **terminal and not retried**: it is
deterministic, so three attempts would reach the same answer and cost three
FFmpeg passes. Only a timeout or a transient storage failure is retried, with
exponential backoff via `not_before`.

### The output object

`remediated/{output_video_id}/output.mp4` — a **new** object under a **new**
video id, encrypted with SSE-S3. Three independent reasons the original cannot
be touched:

1. the source is read through `source_store.materialise`, which downloads to a
   temporary directory and only ever reads the S3 object;
2. the output key is built from a freshly minted video id under a prefix
   nothing else writes;
3. `reconstruct` refuses outright if asked to write over its own input.

A test asserts the source object's bytes are unchanged after a run, and that
nothing wrote to the `sources/` prefix at all.

### The output is a first-class video

It is registered in `videos` with its own id, owned by the same user, carrying
`derived_from_video_id`, `derived_from_remediation_id` and
`is_remediated_output`. That is what lets the **existing** pipeline analyse it
and the **existing** playback route serve it with no special case — and it is
why `source_store.verify_key_belongs_to` now accepts two prefixes per video id
rather than one. The invariant it protects is unchanged: *the key names **this**
video*.

## 6c. Execution, concurrency and recovery

The work runs in the **same worker process** that already drains the video
queue (`backend/worker.py`), using the **same** conditional-claim-under-a-lease
mechanism as `video_repo` — not a new queue service, and not a second source of
truth for jobs. A deployment still runs exactly two processes.

A record is claimable only when it is `asset_ready`, **its owner has explicitly
requested execution** (`execution_requested`, written before the route
responds), its backoff has elapsed, and its attempts are not exhausted. An
attached image alone does not start anything.

| Field | Role |
| :-- | :-- |
| `claim_id` | uuid4 minted by the winning worker — the fencing token |
| `lease_expires_at` | after which the claim is considered dead |
| `not_before` | earliest re-claim instant, set by a retryable failure |
| `attempt` | bounded by `MAX_EXECUTION_ATTEMPTS` (3) |

Every subsequent write passes `claim_id`, making it conditional. So a worker
whose record was reclaimed cannot attach **its** output or **its** verification
to a newer attempt — which, unlike a lost video job, would otherwise associate
the wrong file with a compliance claim. A test drives exactly that race.

### What a crash leaves behind, and who heals it

The object is uploaded **before** its video record, and the record is written
**before** `applied`. So:

| Crash point | What is left | Who heals it |
| :-- | :-- | :-- |
| Before the upload | Nothing | — |
| Between upload and record write | An S3 object no record names | Compensated immediately on that path; the sweep requeues with a **new** output id, so a retry never overwrites the previous attempt's object |
| Mid-run (worker dies) | `reconstructing` with a lapsed lease | `remediation_repo.reclaim`, conditional on the **dead** worker's claim id, so a live-but-slow worker is never robbed |
| After `applied`, before submission | `applied` with the output in `uploaded` | `remediation_executor.resume_applied` |
| After submission | `verifying` | `verification.advance`, from the worker sweep or a status read |

**Execution is at-least-once, NOT exactly-once.** An interrupted attempt is
retried from the beginning and produces a new output video; the previous
attempt's object is retained rather than deleted, because it is real and an
operator may need it. This is stated rather than claimed otherwise.

## 6d. How verification is decided

`backend/verification.py` — the **only** module permitted to move a record to
`verified` or `verification_failed`.

### Not evidence

* FFmpeg exiting 0.
* The owner having approved the proposal.
* A provider returning bytes.
* The output video existing and playing.
* **The original video's analysis results.** A test asserts the query is keyed
  by the output's id, not the source's.
* A completed job that audited **zero frames** — its empty detections list
  reads exactly like a clean video and is evidence of nothing.
* A storage failure reading the results. That defers; it never decides.

### Evidence

A **completed** analysis job for the output video, whose per-frame results were
persisted by the normal pipeline, read back from the frame store keyed by the
output's own id, with at least one audited frame. The job's owner is checked
against the remediation's, so a crossed link cannot verify one user from
another's data.

### The target is matched by category and time

Not by index: re-analysis of a different file produces its own frames in its
own order. A detection in the output is the same finding when its category
matches (trimmed, case-insensitively) and its timestamp is within
`TIMESTAMP_TOLERANCE_SECONDS` (1.5s) of the original's — a little wider than
one 1 fps sampling interval, because being slow to declare success is the safe
direction of error. A target with no timestamp matches on category **anywhere**
in the output, deliberately: without a time we cannot show the finding moved,
so we must not claim it was removed from one place.

### Three outcomes, never conflated

| Field | Question it answers |
| :-- | :-- |
| `target_resolved` | Is the targeted finding gone from the output? |
| `policy_passed` | Does the output satisfy `VERIFICATION_POLICY`? |
| `other_findings` | What else did the output's analysis report? |

`null` for the first two means **no verdict** — not `false`.

| Policy | `policy_passed` when |
| :-- | :-- |
| `target_only` (default) | the target is gone. Other findings are recorded and shown but do not block — a remediation addresses **one** finding, and a video with two problems should not report the first fix as a failure. |
| `clean_output` | the target is gone **and** the output carries no findings at all. |

The record reaches `verified` only when `policy_passed` is true,
`verification_failed` when the analysis completed and it is false, and
terminal `failed` with `error_code: verification_inconclusive` when the
analysis finished but cannot support a conclusion — because
`verification_failed` asserts that a re-analysis ran and **disagreed**, which
is a stronger claim.

### What is persisted as evidence

Enough to explain the verdict without re-running anything: the policy, the
evaluation time, the source and output video ids, the analysis job id and its
state, the frame counts (extracted / audited / failed), the target's category
and timestamp, the tolerance used, the three outcome fields, the detections
that still match the target, the other findings, and a reader-facing `reason`.
No storage key, media token or signed URL — a test asserts that.

## 6e. The UI contract

`frontend/app/components/RemediationPanel.tsx`, with the wording owned by
`frontend/app/lib/remediation.ts`. Labels state what has happened and name the
step outstanding:

| State | Label |
| :-- | :-- |
| `approved` | "Approved, awaiting a replacement image" |
| `asset_ready` | "Image ready, video unchanged" |
| `reconstructing` | "Building a new video, original unchanged" |
| `applied` | **"New video built, not yet checked"** |
| `verifying` | "Checking the new video" |
| `verified` | "Checked: the finding is gone" |
| `verification_failed` | "Checked: the finding is still there" |

The word **"compliant" appears in no label at all** — not even the verified one,
because `verified` under the default policy means *the targeted finding is
gone*, which is not *the video is compliant*. A test enumerates every state and
asserts it. "Original unchanged" is shown at every stage. Every non-proposed
state also carries "Not a compliance sign-off".

Other guarantees, each with a test:

* `verified` is rendered from the server's `is_compliance_claim` and
  `verification` evidence, never from the state string — a record claiming
  `verified` whose evidence says otherwise renders as "No conclusion";
* progress is the backend's **named stage** for the output's analysis job; no
  percentage is ever shown, and the panel asserts `%` does not appear;
* the playback URL is fetched on demand and 404s until an output exists, so
  there is no placeholder player and no dead download action;
* other findings are rendered in their own block, below the verdict, with "they
  are not resolved" — never merged into it;
* polling runs only while the record is executing, stops on a terminal state
  and on unmount, and schedules the next poll only after the previous settles;
* a retry is offered for a **failed build** with attempts left, and never for a
  check that came back negative — the same image would build the same video.

## 7. Known limitations

- **Nothing has been validated against real AWS or Bedrock.** Every test mocks
  at the service boundary. No provider has ever been called, no S3 object has
  been written, and no Bedrock analysis has run.
- **FFmpeg was not available where Phase 9 was written.** `which ffmpeg` found
  nothing, so `backend/tests/test_integration_ffmpeg_reconstruction.py` is
  **skipped** — 13 tests, each with a precise skip reason. The reconstruction
  logic is covered by subprocess-boundary tests that stub `ffmpeg.probe` and
  `run_async`, which pin the filter graph, the audio handling, the refusals and
  the cleanup. **No real video has been built by this code.** Install FFmpeg
  and run `pytest -m requires_ffmpeg` before trusting the output.
- **Execution is at-least-once, not exactly-once.** An interrupted attempt
  re-runs from the beginning and produces a new output video; the previous
  attempt's object is retained. No deduplication across attempts is claimed.
- **Delivery is polled, not pushed.** A requested reconstruction waits up to
  one worker poll interval, and a verdict waits up to one recovery interval
  unless a client reads the status route first.
- **Verification depends on the re-analysis, so it inherits its cost and its
  accuracy.** Analysing an output bills Bedrock per frame exactly like the
  original did, and detection accuracy is unmeasured — so `verified` means
  "this model no longer reports that finding there", not "the issue is gone".
- **A scaled overlay is a concealment, not a repair.** Hard edges, no grain
  matching, no motion tracking. A viewer will see a rectangle.
- **The whole clip is re-encoded** by the single video pass, so the output is
  one generation lossier than the original even outside the approved window.
  Audio is copied and therefore unaffected.
- **Proposals are not brand-policy determinations.** There is no configurable
  brand-rule system — one static prompt in `backend/prompts.py`. A proposal
  says what the model reported and attributes it; it cites no guideline,
  trademark or regulation, because none is configured and inventing one would
  be worse than having none. The limitation text is attached to every proposal
  so a reviewer sees it with the proposal, not in documentation.
- **A model explanation is not evidence.** The model's `description` is quoted
  as its claim, never restated as fact, and no second model call explains the
  first.
- **1 fps sampling** means a neighbouring frame can contain the same issue
  with no separate finding, so one proposal does not cover a whole shot.
- **Detection accuracy is unmeasured**, so the base rate of proposals worth
  approving is unknown.
- **Approval is per-finding**, with no bulk action. Deliberate for now: a bulk
  approve over unmeasured detections is a way to approve things unread.
- **The panel polls only while work is in flight.** Outside those states a
  decision updates the record in place and other changes need a reload.
- **No audit export.** Decisions and verification evidence are stored with who
  and when, but there is no report endpoint.
- **One remediation per finding, one finding per output.** Building a second
  correction for a different finding produces a second output video from the
  ORIGINAL source, not a cumulative one. Chaining corrections is not
  implemented.
- **No way to promote an output to be the new source.** The output is a
  separate video the owner can play and analyse; it does not replace the
  upload, and nothing offers to make it do so.

## 8. The four steps, and where they stand

Phase 8 listed these as "none of it exists". Three now do.

| Step | Status |
| :-- | :-- |
| 1. Obtain a validated replacement image | **Done** via upload (§6a). **Not** via generation (§4, §6). |
| 2. Build an output video as a **new** object | **Done** (§6b). Resolves §9 q3. The original is never overwritten. |
| 3. Re-analyse that output through the existing pipeline | **Done** (§6c) — its own video record, its own job, its own persisted per-frame results. |
| 4. Move `verifying → verified` only from those results | **Done** (§6d). A re-analysis that still reports the finding lands in `verification_failed`, which is terminal and **not** a clean verdict. |

**But none of it has run for real.** Every step above is implemented and
tested at its service boundaries; step 2 has never executed against the real
FFmpeg binary on this machine, and steps 1-4 have never touched real S3,
DynamoDB or Bedrock.

## 9. The reconstruction decision (resolves §9 q3)

> **Video reconstruction is in release scope, built from an owner-supplied
> replacement image, as a localized overlay over the approved region — and
> reported as exactly that.**

Why this shape rather than the alternatives:

* **Why an overlay, not a frame re-stitch.** A re-stitch from the 1 fps frames
  discards audio and changes every frame; the output would differ from the
  original everywhere, which is both a worse artefact and a dishonest one. See
  §6b.
* **Why a new object rather than editing in place.** An original upload is the
  user's evidence of what they submitted. Overwriting it would destroy that,
  and there is no undo for an S3 overwrite that has already been versioned
  away. The output being a separate video also means the existing pipeline and
  playback route need no special case.
* **Why an owner-supplied image rather than waiting for a provider.** The
  provider's only job is to produce bytes. Blocking the entire workflow on an
  unverifiable wire format would have left the three *verifiable* stages
  unbuilt, and those are where the honesty risk lives: the verdict, not the
  pixels.
* **Why not promote the output to replace the source.** That is a product
  decision with real consequences (it would change what every prior analysis
  refers to), and nothing in this phase needed it. Left open.

### What an operator must do before relying on it

1. **Install FFmpeg** so `ffmpeg` and `ffprobe` are on PATH, in the API image
   *and* the worker image. Without it `RECONSTRUCTION_ENABLED=false` is the
   honest setting, and the API will report the capability as absent.
2. **Run `pytest -m requires_ffmpeg`** and confirm the 13 real-binary tests
   pass. They generate their own clips with FFmpeg's synthetic sources, so no
   fixture media is needed.
3. **Deploy the updated `infra/cloudformation/storage.yaml`**, which adds
   lifecycle rules for `remediation-assets/` and `remediated/`. Phase 9 did
   not deploy it, and nothing in AWS was touched.
4. **Apply the updated `infra/iam_policy_least_privilege.json`**, which adds
   those two prefixes to the object statement and to the delete statement
   (compensating cleanup only). Nova Canvas is still **not** granted.
5. **Confirm cost.** A reconstruction is one FFmpeg pass, but the re-analysis
   it triggers bills Bedrock **per frame of the output**, at the same rate as
   the original analysis. A verified correction therefore costs roughly two
   analyses of one clip.
6. **Decide `VERIFICATION_POLICY`.** The default `target_only` verifies when
   the targeted finding is gone, whatever else the output contains. If your
   product promise is a clean video, set `clean_output` — and expect more
   corrections to report as failed.

### What remains for a later phase

* A real image provider (§4, §6) — still the one genuinely missing capability.
* Chained corrections: a second remediation currently rebuilds from the
  original, not from the first output.
* Promoting an output to replace its source, if that is ever wanted.
* An audit export of decisions and verification evidence.
* Measured detection accuracy, without which `verified` cannot be given a
  confidence of its own.
