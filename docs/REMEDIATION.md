# Remediation — scope decision, contract, and what remains

**Phase 8, 2026-10-21.** This document resolves `CLAUDE.md` §9 question 4 and
is the authority on what remediation does in this build.

It resolves **only** question 4. Questions 2 (MongoDB vs DynamoDB), 3 (video
reconstruction), 7 (Nova Act) and 9 (deployment target) are untouched and
remain open.

---

## 1. The decision

> **Remediation is in release scope as a reviewed proposal workflow.
> Automated image generation is not implemented, and no Nova Canvas adapter
> ships.**

What that means concretely:

| Capability | Status |
| :-- | :-- |
| Propose a remediation for a persisted finding | **Implemented** |
| Explain what would change, on what basis, and what it cannot guarantee | **Implemented** |
| Owner approval / rejection / withdrawal, enforced server-side | **Implemented** |
| Confidence threshold actually read and enforced | **Implemented** |
| Staleness detection (finding changed → proposal superseded) | **Implemented** |
| Generate a corrected frame image | **Not implemented** — contract only |
| Apply an asset to a video | **Not implemented** (Phase 9) |
| Verify compliance by re-analysis | **Not implemented** (Phase 9) |

**No asset has ever been generated by this system, and no video has ever been
modified by it.** There is no code path that can do either.

### Why generation is not implemented

The roadmap's own instruction for this phase is: *"Verify the payload schema
against current Bedrock documentation; **do not guess**."* The schema cannot
be verified from anything available here:

1. **The pinned SDK does not describe it.** `bedrock-runtime`'s `InvokeModel`
   takes `body` as an opaque **blob** — verified directly against this
   repository's own dependency:

   ```
   botocore 1.43.114
   data/bedrock-runtime/2023-09-30/service-2.json.gz
   InvokeModelRequest.body -> shape "Body", type "blob"
   ```

   So boto3 validates nothing about a Canvas request. There is no generated
   client, no typed model, no shape to read.

2. **No existing code defines it.** The one prior attempt,
   `audit_manager.remediate_frame` (deleted in Phase 5; recoverable at
   `94205bb^:backend/audit_manager.py`), carried its own admission in a
   comment — *"Since I don't have the exact Canvas schema confirmed, I'll use
   a placeholder structure"* — had its `invoke_model` call commented out, and
   encoded image bytes with `.decode('latin1')`, which is not a valid encoding
   for a Bedrock image field under any schema. It returned its input unchanged
   while its caller recorded `remediated=True`. It is evidence of the bug, not
   of the API.

3. **No document here specifies it.** `docs/planning.md` names the model and
   nothing else. `infra/iam_policy_least_privilege.json` has kept the Canvas
   grant commented out since Phase 3.5 for precisely this reason.

A guessed adapter would be worse than none: it would look implemented, pass
its own mocked tests (the mock would encode the same guess), and fail only
against the real service — after an operator had granted it model access and
pointed it at live customer video.

### Why the review workflow was worth building first

Generation is the *last* missing piece, not the first. Even a working Canvas
call produces a frame image that nothing can consume: assembling it into an
output video is Phase 9, which is gated on its own unresolved decision (§9
q3). Shipping generation first would produce assets with no consumer.

The review workflow, by contrast, is the human-in-the-loop gate the roadmap
asks for (Phase 8 task 4, *"a human-in-the-loop queue … planned, entirely
absent"*), is fully implementable with no AWS dependency, and is testable end
to end.

## 2. The domain model

### States

Defined in `backend/remediation_state.py`. Each is a different statement about
the world and **none may be inferred from another**:

| State | What it asserts |
| :-- | :-- |
| `proposed` | A change has been described. Nobody agreed to it; nothing generated; nothing changed. |
| `approved` | An authenticated owner agreed it should be attempted. **Still nothing generated.** |
| `processing` | A provider call is in flight. It may fail. |
| `asset_ready` | A validated asset exists in storage. The source video is **unchanged** — a candidate, not a correction. |
| `applied` | The asset was incorporated into an output video. Its compliance is **unknown**. |
| `verifying` | A fresh analysis of that output is running. |
| `verified` | A completed analysis of the output persisted results supporting the claim. **The only state that may be called compliant.** |
| `rejected` | The owner declined. Terminal. |
| `cancelled` | Withdrawn before anything consequential. Terminal. |
| `superseded` | The video was re-analysed and the finding changed, so the proposal no longer describes anything real. Not a failure. Terminal. |
| `failed` | A stage failed; `error_summary` says which, safely. Terminal. |
| `verification_failed` | A re-analysis ran and did **not** support the claim. **Emphatically not clean.** Terminal. |

```
proposed ─► approved ─► processing ─► asset_ready ─► applied ─► verifying
   │           │            │                                      │
   ├► rejected │            ├► failed                              ├► verified
   ├► cancelled├► cancelled │                                      └► verification_failed
   └► superseded└► superseded└► superseded
```

Properties the transition table enforces, each with a test:

- `verified` is reachable **only** from `verifying`. "Verified" therefore means
  a re-analysis ran — not that somebody decided it was fine.
- `applied` is reachable only from `asset_ready`; `processing` only from
  `approved`. Approval cannot be skipped and generation cannot be skipped.
- No state transitions to itself. Repeated decisions are handled as idempotent
  no-ops by the routes, so a retry cannot overwrite `approved_at`.
- Terminal states have no exit. A new attempt is a **new proposal**, so the
  record of what was agreed stays intact.
- `superseded` is unreachable once an asset exists: the object is real whatever
  the finding now says, and hiding it would orphan it.

### What this build can reach

`REACHABLE_IN_THIS_BUILD = {proposed, approved, rejected, cancelled, superseded}`

Everything else — including `failed` — is in `UNREACHABLE_IN_THIS_BUILD`, and
the two sets are asserted to partition the enum. `test_remediation_routes.py`
drives every route in every order over one record and asserts the unreachable
states never appear.

`failed` is unreachable deliberately: with no provider there is nothing that
can fail, and answering "generation is not configured" by marking the record
`failed` would make a terminal claim about the remediation when the only thing
missing is a deployment capability.

### Identity and staleness

A finding is addressed positionally: **`(video_id, frame_number,
detection_index)`**. That address is not stable — `analyzer._record_frame_result`
overwrites a frame's row, and a second Bedrock call can return a different
number of violations in a different order.

So every record also stores a **fingerprint**: a SHA-256 over the finding's
category, description, risk level, confidence and bounding box (formatted, so a
`Decimal` from DynamoDB and the `float` it was written from hash identically).
Before any consequential action the finding is re-read and re-fingerprinted; a
mismatch moves the record to `superseded` and the request answers 409.

The fingerprint deliberately excludes `detection_index` (the address, not the
content) and `timestamp_seconds` (derived from the frame number).

### Storage

MongoDB collection **`remediations`**, beside `videos` and `users`.

- **Not DynamoDB:** the lifecycle needs a conditional write keyed on the
  record's current state, which is exactly the
  `update_one(filter_including_state, {"$set": …})` + `modified_count` pattern
  `video_repo` already uses. One concurrency idiom, not two. §9 q2 stays open
  and this moves with whatever it decides.
- **Not a field on the `videos` document:** a video has many findings with
  independent lifecycles; embedding an unbounded, individually-transitioning
  array in the document the worker conditionally updates on every heartbeat
  would make two unrelated writers contend on one document.

**Migration:** purely additive. The collection is created on first insert,
`ensure_indexes` is idempotent, and no existing document is read or written. A
deployment that never calls a remediation route never creates the collection;
rolling back to a build without this module leaves it unread. `db_init`
creates the indexes (`remediation_id` unique, `owner`, `video_id`, `state`)
alongside the existing ones, non-destructively.

## 3. The API

All routes require a bearer token. Every one resolves ownership from the
video's ownership record or the remediation's stored `owner`; a request body
never carries an owner, a role, or an approver.

| Method | Path | Purpose |
| :-- | :-- | :-- |
| `GET` | `/remediations/capabilities` | What this deployment can do |
| `POST` | `/remediations` | Propose for one finding |
| `GET` | `/remediations?video_id=…` | List the caller's records for a video |
| `GET` | `/remediations/{id}` | One record |
| `POST` | `/remediations/{id}/approve` | Record the owner's approval |
| `POST` | `/remediations/{id}/reject` | Record the owner declining |
| `POST` | `/remediations/{id}/cancel` | Withdraw, including after approval |
| `POST` | `/remediations/{id}/execute` | Attempt generation — **always 503 today** |

### Status codes and what they mean

| Code | When |
| :-- | :-- |
| 201 | A proposal was created |
| 200 | A decision applied, or a repeat of one already applied (idempotent), or a proposal already existed for this finding |
| 400 | Malformed video id |
| 401 | No token, an expired token, or a media token (scope separation) |
| 404 | No such record/finding, **or it is not yours**, or remediation is disabled |
| 409 | Wrong state, a stale finding, a below-threshold gate, the per-video cap |
| 422 | Malformed payload, or a stored finding that cannot support a review |
| 502 | The analysis store could not be read (never confused with a missing finding) |
| 503 | No image provider is available |

### Authorization, stated once

- A record that does not exist and one belonging to someone else both answer
  **404**, so these endpoints cannot enumerate ids.
- `approved_by` is written from `user["sub"]` and nothing else. A body field
  named `approved_by`, `owner` or `state` is ignored — there is a test.
- The repository layer filters **every** read and **every** conditional write
  by `owner`, so a mistake in a route cannot become a cross-tenant read.
- Concurrency is the conditional write: the filter includes the current state,
  so of two racing decisions the loser matches zero documents and gets 409.
- Proposals require the video's analysis to be `completed`. A finding is only
  a settled fact once the job reached the state meaning analysis finished and
  its results were persisted.

### Added to an existing endpoint

`GET /violations/{video_id}` now includes **`detection_index`** on each
detection. Additive and backward-compatible: no field was removed or renamed,
and a test asserts the existing keys are still present. It is needed because
`/violations` flattens detections across frames, so the browser cannot derive
a finding's index within its frame; deriving it from array position would work
only by undocumented convention and would break under different pagination.

## 4. The provider contract

`backend/image_provider.py`. One method, no storage access, no identity.

```python
class ImageProvider(Protocol):
    name: str
    def is_available(self) -> bool: ...          # no network I/O
    def unavailable_reason(self) -> str | None: ...
    def generate(self, request: GenerationRequest) -> GenerationResult: ...
```

`GenerationRequest` carries the image bytes, a **validated** region
(`[ymin, xmin, ymax, xmax]`, 0–1000, already checked for length, type, range
and ordering) and an instruction. It deliberately carries **no** S3 key, media
token, username or raw model text, so a provider cannot reach storage or
identity on its own. It is frozen, so a provider cannot mutate the region.

### Error contract

| Exception | `retryable` | Meaning |
| :-- | :-- | :-- |
| `ProviderUnavailable` | `False` | Not configured. No retry configures a provider. |
| `InvalidProviderOutput` | `False` | Answered, but not with a usable image. |
| `ProviderError` | explicit | Anything else; set **at the raise site**, never inferred from a message — the `source_store` rule. |

### Output validation

`validate_image_bytes` treats provider output as untrusted and returns the
content type **derived from the bytes**, ignoring whatever the provider
declared. It rejects: non-bytes, empty, under 64 bytes, over 16 MiB, and
anything whose magic number is not JPEG or PNG — which covers a JSON error
body, an HTML error page and a PDF, all of which arrive as bytes with a 200.

**A 2xx response is not evidence of an image.** Tests cover every case above
with deterministic payloads.

### What ships

`NullImageProvider` only. It reports `is_available() == False` and `generate`
**always raises** — it never returns input bytes, a placeholder, or a
fabricated result. That is the entire difference between this phase and the
deleted `remediate_frame`, and there is a test named for it.

Configuring `REMEDIATION_IMAGE_PROVIDER=nova-canvas` returns a
`NullImageProvider` that reports the configured name with a specific reason
naming the unverified wire format, rather than an opaque "unknown provider".
An unrecognised value is a `ConfigurationError` at startup.

## 5. Configuration

| Variable | Default | Purpose |
| :-- | :-- | :-- |
| `REMEDIATION_ENABLED` | `true` | The proposal/review workflow. `false` makes every route 404. |
| `REMEDIATION_IMAGE_PROVIDER` | `none` | `none` or `nova-canvas`; neither generates. Anything else fails at startup. |
| `REMEDIATION_MIN_CONFIDENCE` | `0.8` | Threshold `execute` enforces. The figure `docs/planning.md` has specified since Phase 1 — this is the first code to read it. |
| `MAX_REMEDIATIONS_PER_VIDEO` | `200` | Per-video cap. |

The confidence gate records one of `pass` / `below_threshold` /
`not_reported` on every proposal. A finding with **no** reported confidence
does not pass: absent is not the same as high, and `detections.py` keeps it
absent rather than defaulting it. Review is never gated — a human should be
able to look at a low-confidence finding; only generation is refused.

**No new IAM permission is required**, because no code path calls a provider.
`infra/iam_policy_least_privilege.json` still withholds
`amazon.nova-canvas-v1:0` and its `_NOT_GRANTED` note now explains why after
Phase 8. Nothing in `infra/` was deployed, and no live AWS resource was
touched.

## 6. Implementing a real provider — the checklist

Everything a future phase and its operator must supply. Do not start until
`CLAUDE.md` §9 q3 (reconstruction) is also decided, or the assets will have no
consumer.

**Must be verified first (the blocker):**

1. The Nova Canvas `INPAINTING` request schema from authoritative Bedrock
   documentation: field names, nesting, how image and mask are encoded
   (base64, not `latin1`), size and dimension limits, and the response
   envelope. Write the citation into the adapter's docstring.

**Then, in code:**

2. Implement `ImageProvider` in a new `backend/nova_canvas_provider.py`.
   Build the client through `aws_clients` so it gets finite timeouts and a
   bounded retry budget — an unbounded call keeps a dead worker heartbeating
   and its job is never recovered.
3. Build the mask from the validated `region` and the image's **own**
   dimensions. This re-adds a **Pillow** dependency, removed in Phase 5 —
   declare and pin it in `backend/requirements.txt` (`test_dependencies.py`
   enforces that).
4. Classify every failure at its raise site. Throttling and timeouts are
   retryable; a validation rejection or an unsupported image is not.
5. Pass every byte through `validate_image_bytes` before it reaches storage.
6. Store assets under a **new** S3 prefix with server-generated keys, e.g.
   `remediated/{video_id}/{remediation_id}.png`. Add it to
   `aws_resources.MANAGED_PREFIXES`, to the IAM statement and to the bucket
   lifecycle rules together — the prefix list is a contract across all three.
   **Never overwrite the original**: `sources/` and `frames/` stay untouched.
7. Serve assets through the project's existing authorization approach (a
   short-lived scoped media token), never a public or presigned URL in a
   response body, and never log a signed URL.
8. Run generation on the **existing durable worker**, not a second queue:
   persist the claim before acknowledging, keep the lease and fencing token,
   bound the attempts. Remove `processing`/`asset_ready` from
   `UNREACHABLE_IN_THIS_BUILD` and update the test that asserts the partition.
9. Add provider tests with malformed, empty, oversized, unsupported and failed
   responses — the contract tests already exist; add the adapter's own.

**Operator steps:**

10. Request Bedrock model access for `amazon.nova-canvas-v1:0` in the region.
11. Add the `bedrock:InvokeModel` grant for that model ARN to the IAM policy
    and remove its `_NOT_GRANTED` entry.
12. Set `REMEDIATION_IMAGE_PROVIDER=nova-canvas`.
13. **Confirm cost.** Generation is billed per image, on top of the per-frame
    Nova Pro analysis cost.

## 7. Known limitations

- **Nothing has been validated against real AWS or Bedrock.** Every test mocks
  at the service boundary. No provider has ever been called.
- **Proposals are not brand-policy determinations.** There is no configurable
  brand-rule system — one static prompt in `backend/prompts.py`. A proposal
  says what the model reported and attributes it; it cites no guideline,
  trademark or regulation, because none is configured and inventing one would
  be worse than having none. The limitation text is attached to every proposal
  so a reviewer sees it with the proposal, not in documentation.
- **A model explanation is not evidence.** The model's `description` is quoted
  as its claim, never restated as fact, and no second model call explains the
  first.
- **1 fps sampling** means a neighbouring frame can contain the same issue
  with no separate finding, so one proposal does not cover a whole shot.
- **Detection accuracy is unmeasured**, so the base rate of proposals worth
  approving is unknown.
- **Approval is per-finding**, with no bulk action. Deliberate for now: a bulk
  approve over unmeasured detections is a way to approve things unread.
- **The detail view does not poll** remediation state; a decision updates the
  record in place, and other changes need a reload.
- **No audit export.** Decisions are stored with who and when, but there is no
  report endpoint.

## 8. What Phase 9 must do before a corrected video can be claimed

In order. None of it exists.

1. **Generate an asset** — §6 above.
2. **Reconstruct an output video** from the original frames plus remediated
   ones, written as a **new** object. Resolves §9 q3. The original upload is
   never overwritten.
3. **Re-analyse that output** through the existing pipeline, producing its own
   job and its own persisted per-frame results.
4. **Only then** may a record move `verifying → verified`, and only when those
   persisted results support the claim. A re-analysis that still reports the
   finding must land in `verification_failed`, which is terminal and is **not**
   a clean verdict.

Until all four exist, the honest rendering of an approved remediation is
"approved, nothing generated" — which is what the UI says.
